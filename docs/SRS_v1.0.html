1. Introduction

1.1 Purpose

This document specifies the requirements for SHIELD Walk, a mobile and web platform that helps people choose safer walking routes, stay protected during a walk, and gives city and campus authorities street-level safety data. It is the reference for design, implementation, testing and acceptance.

1.2 Scope

SHIELD Walk consists of five deliverables:

  1. Mobile app (Android first; React Native / Expo development build) for walkers and guardians.
  2. Backend services (FastAPI, PostgreSQL + PostGIS, Redis) for routing scores, alerts, live location and sync.
  3. On-device AI (audio distress detection and motion/fall detection) that runs without internet.
  4. Offline alert path (local queue and native SMS) that works with no data connection.
  5. Authority dashboard (web) for responders and city/campus analysts.

Out of scope for v1: iOS silent-SMS fallback (not permitted by iOS), wearable apps, federated learning, volunteer-responder network, payments, and any guarantee that help will arrive. SHIELD Walk is an assistive safety tool and does not replace emergency services.

2.2 Product functions (summary)

Safety-scored route comparison; live trip sharing with deviation alerts; automatic distress detection; one-tap and hardware-button SOS; silent duress PIN; offline SMS alerts with later sync; guardian escalation chain; encrypted evidence capture; post-walk ratings and hazard reports; authority dashboard with heatmaps; auto-generated incident report.

2.4 Operating environment

  • Mobile: Android 10+ (target API 34), ARM64, minimum 3 GB RAM, GPS and microphone required. Delivered as an Expo development build / EAS build (not Expo Go).
  • Backend: Linux, Docker Compose, Python 3.11+, PostgreSQL 15 with PostGIS, Redis 7.
  • Dashboard: Latest Chrome, Edge and Firefox, 1280 px wide and above.

2.5 Design and implementation constraints

  • C-1. Silent SMS sending is possible only on Android; the fallback is not available on iOS.
  • C-2. Google Play restricts the SMS permission. The hackathon and pilot builds are sideloaded or distributed through internal testing; a Play release needs a compliant alternative (SMS intent with user tap, or default-handler exemption).
  • C-3. Commercial SMS in India requires DLT registration with the gateway.
  • C-4. Background microphone and location need foreground services with correct types on Android 14+, plus a persistent notification.
  • C-5. Raw audio must not leave the device unless an alert is active.
  • C-6. Safety scores must use physical street features, never demographics or neighbourhood identity.

2.6 Assumptions and dependencies

  • A-1. Walkers carry a smartphone with a SIM and a basic cellular plan (needed for SMS).
  • A-2. OSM coverage is adequate in the pilot area (verify before launch).
  • A-3. Guardians install the app or accept SMS-only alerts.
  • D-1. Availability of the routing API and SMS gateway.
  • D-2. A labelled audio dataset (Scream/Non-scream and ESC-50) is available for fine-tuning.

3. System Features and Functional Requirements

3.1 Account, onboarding and security settings (AUTH)

ID Requirement P Rel
AUTH-1 The system shall register a user with phone number, name and OTP verification. M MVP
AUTH-2 The system shall issue short-lived access tokens (15 min) and refresh tokens (30 days) and allow revocation. M MVP
AUTH-3 The user shall set a normal PIN and a different duress PIN; the app shall reject identical PINs. M MVP
AUTH-4 PINs shall be stored only as salted slow hashes (Argon2id or bcrypt) on the server and in Android Keystore-protected storage on the device. M MVP
AUTH-5 The app shall limit PIN attempts (5 failures, then escalating lockout) without revealing which PIN type failed. M MVP
AUTH-6 The onboarding wizard shall collect: profile, PINs, at least one guardian, permissions (location, microphone, SMS, notifications, battery optimisation exemption). M MVP
AUTH-7 The user shall be able to delete their account and all personal data. M Pilot

3.2 Guardians and contacts (GRD)

ID Requirement P Rel
GRD-1 The user shall add up to 5 guardians with name, phone and priority order. M MVP
GRD-2 A guardian shall accept an invitation by SMS link; unverified guardians still receive SMS alerts but not live tracking. M MVP
GRD-3 The app shall display a key fingerprint (QR code) for each guardian so the walker can verify the encryption key out of band. S Pilot
GRD-4 The guardian shall see a live map, status and trip details for walks shared with them. M MVP
GRD-5 The guardian shall be able to acknowledge an alert, call the walker, or escalate to responders with one tap. M MVP
GRD-6 The walker shall be able to pause or stop sharing at any time. M MVP

3.3 Safe route planning (ROUTE)

ID Requirement P Rel
ROUTE-1 The user shall search a destination (text or map pin) and set origin (current location by default). M MVP
ROUTE-2 The system shall obtain 2 to 3 walking route alternatives from the routing provider. M MVP
ROUTE-3 The system shall split each route into segments and compute a Safety Score per segment and per route using the model in Section 6.1. M MVP
ROUTE-4 The app shall show routes ranked by Safety Score, labelling the fastest and safest, with distance, time, and score breakdown (lighting, activity, ratings). M MVP
ROUTE-5 Segments scoring below 40 shall be highlighted as "caution" on the map. S MVP
ROUTE-6 Route computation shall use the time of day (day, evening, night) to select weights. M MVP
ROUTE-7 The system shall show nearby Safe Stops (police stations, hospitals, open pharmacies, 24-hour shops, verified partner shops) along the route. S Pilot
ROUTE-8 The app shall never state that a route is "safe"; it shall say "higher safety score" and show a disclaimer. M MVP
ROUTE-9 The system shall cache scores per segment and refresh them at least daily or after new ratings. S Pilot

3.4 Walk tracking and live sharing (WALK)

ID Requirement P Rel
WALK-1 The user shall start a walk on a chosen route; the app shall begin foreground tracking with a persistent notification. M MVP
WALK-2 Location shall be sampled adaptively: every 10 s in normal mode, every 2 s after any trigger or deviation, and every 30 s when battery is under 15%. M MVP
WALK-3 The system shall stream location to guardians in near real time via WebSocket, with HTTP batching as a fallback. M MVP
WALK-4 The system shall flag route deviation when the walker is more than 150 m from the chosen route for more than 30 s (thresholds configurable), then prompt the walker and notify guardians if not dismissed within 20 s. M MVP
WALK-5 The system shall flag an unexpected long stop (no movement beyond 30 m for 5 min mid-route). S Pilot
WALK-6 The user shall be able to set a check-in timer (dead-man's switch); failing to confirm in time triggers the alert flow. S Pilot
WALK-7 On arrival (within 30 m of the destination), the app shall end the walk, notify guardians, and show the rating prompt. M MVP
WALK-8 Low battery survival mode: at 15% battery the app shall send a final location to guardians and drop to minimal sampling. S Pilot

3.5 Distress detection (DET)

ID Requirement P Rel
DET-1 During an active walk (or when enabled), the app shall run an on-device audio classifier on 0.975 s windows with no network access required. M MVP
DET-2 The audio model shall be a pretrained embedding model (YAMNet or equivalent) with a small classification head fine-tuned for distress sounds, quantised for TFLite. M MVP
DET-3 The audio detector shall trigger the pre-alert when scream probability is at least 0.80 in 3 of 5 consecutive windows (default; tunable). M MVP
DET-4 The app shall detect keywords ("bachao", "help", "chhodo") using a keyword-spotting model, as an additional trigger. C Later
DET-5 The app shall detect falls and struggles from accelerometer and gyroscope: impact above 2.5 g followed by 10 s of stillness, or sustained erratic motion pattern. S Pilot
DET-6 A composite threat score shall combine audio, motion and context (night, high-risk area) using weights in Section 6.2. S Pilot
DET-7 The model shall be evaluated on a held-out set; the team shall report precision, recall and the false-positive rate per ESC-50 class (crying, laughing, siren, glass breaking). M MVP
DET-8 Raw audio shall be processed in memory and discarded unless an alert becomes active (then see EVID). M MVP

3.6 Alerts, SOS and escalation (ALERT)

ID Requirement P Rel
ALERT-1 The user shall trigger SOS by on-screen long-press (500 ms), by hardware button pattern (power button 5 times or volume combo, where the OS allows), or by in-app voice keyword when enabled. M MVP
ALERT-2 Automatic triggers (DET, WALK-4, WALK-6) shall start a pre-alert: a 10 s countdown with vibration, cancellable only with the normal PIN. M MVP
ALERT-3 A duress PIN entered at cancel shall appear to cancel normally while sending a silent high-priority alert. M MVP
ALERT-4 On alert confirmation, the app shall first write the alert to the local queue (SQLite) with a UUID, then dispatch over all available channels in parallel. M MVP
ALERT-5 Offline path: the app shall send an SMS with name, last known coordinates and a map link to all guardians using the native SMS API, with no data connection required. M MVP
ALERT-6 Online path: the app shall post the alert to the backend, which shall send push notifications to guardians and (if configured) SMS via the gateway and forward to responders. M MVP
ALERT-7 The queue shall retry sync with exponential backoff (up to 5 attempts, then wait for connectivity change) and the API shall treat repeated submissions of the same UUID as idempotent. M MVP
ALERT-8 Escalation chain: if guardian 1 does not acknowledge within 60 s, the system shall notify guardian 2, then guardian 3, then responders (if configured). M MVP
ALERT-9 Emergency numbers (112 or local equivalents) shall be configurable per region and disabled by default until the team has verified that the number accepts SMS in that state. M MVP
ALERT-10 The alert shall move through the states in Section 6.3 and every transition shall be logged. M MVP
ALERT-11 After an alert, the user shall be able to mark it false alarm and give a reason; the reason shall be stored to tune thresholds. S Pilot
ALERT-12 Disguised mode: the app icon and name may be set to a neutral utility (for example "Calculator"), opening SHIELD via a secret input. C Later

3.7 Evidence capture (EVID)

ID Requirement P Rel
EVID-1 When an alert becomes active, the app shall record audio in 30 s rolling chunks. M MVP
EVID-2 Each chunk shall be encrypted on the device with AES-256-GCM using a fresh random key; the key shall be sealed for each guardian with their public key (RSA-OAEP-2048 or X25519 sealed box). M MVP
EVID-3 The server shall store ciphertext only and shall not hold plaintext keys. M MVP
EVID-4 Each chunk shall be hashed (SHA-256) and chained with the previous hash; the head hash shall be submitted to the server for timestamping. S Pilot
EVID-5 Local chunks shall be deleted after upload is confirmed. Upload shall retry when connectivity returns. M MVP
EVID-6 The documentation shall describe the system as "end-to-end encrypted, server cannot read audio", not "zero-knowledge", unless key verification (GRD-3) is implemented. M MVP

3.8 Duress mode (DUR)

ID Requirement P Rel
DUR-1 The duress PIN shall be verified locally first so it works offline; the result shall be reported to the server when possible. M MVP
DUR-2 The UI, timing and animation for the duress and normal PINs shall be identical. M MVP
DUR-3 Entering the duress PIN shall trigger ALERT-4 to ALERT-8 silently (no sound, vibration or visible indicator). M MVP
DUR-4 Duress alerts shall be marked high priority in guardian and responder views. M MVP

3.9 Ratings and hazard reports (RATE)

ID Requirement P Rel
RATE-1 After a walk, the app shall offer a one-tap rating: Lit? Busy? Felt safe? (yes/no each), optional note. M MVP
RATE-2 A rating shall be accepted only for a walk whose GPS trace covers at least 70% of the rated segments. M MVP
RATE-3 The system shall limit users to one rating per segment per walk and 20 ratings per day, and discount ratings that deviate strongly from consensus. M Pilot
RATE-4 Users shall report hazards (broken light, harassment spot, blocked path) with a pin, category and optional photo. S Pilot
RATE-5 Ratings shall be anonymised before appearing on any map or dashboard. M MVP
RATE-6 A moderator shall review reported hazards flagged as abusive. S Pilot

3.10 Authority dashboard (DASH)

ID Requirement P Rel
DASH-1 Responders shall sign in with role-based access and see active alerts on a live map with walker details, last location, trail and acknowledgement status. M MVP
DASH-2 Responders shall be able to acknowledge, assign and resolve alerts, and add notes. S Pilot
DASH-3 Analysts shall see a heatmap of ratings, hazard reports and anonymised incident clusters, filterable by date, time of day and category. M MVP
DASH-4 The dashboard shall list infrastructure gaps (segments with low lighting score and high night usage) as a ranked work list, exportable as CSV. M MVP
DASH-5 Dashboard data shall be aggregated to a minimum cell size (for example 5 incidents or 20 walks) before display, to prevent identification of individuals. M MVP
DASH-6 All dashboard access to personal data shall be written to an audit log. M Pilot

3.11 Reporting (REP)

ID Requirement P Rel
REP-1 After an alert, the walker shall be able to generate a PDF incident report with timeline, trigger type, location trail, evidence hashes and guardian responses. S Pilot
REP-2 The report shall carry a disclaimer and be shareable by the user only (no automatic sending to authorities). M Pilot

5.2 Retention and privacy

  • Walk points: delete 30 days after the walk ends unless attached to an alert.
  • Alert data and evidence: retain for 1 year (or until the user deletes), then delete.
  • Ratings: retain anonymised indefinitely.
  • Dashboard data is aggregated; no raw trails of non-alert walks are visible to authorities.
  • Only data needed for the feature is collected (data minimisation); explicit consent is recorded for location, microphone and contact data.

6. Algorithms and Behaviour Specifications

6.1 Safety Score model

Segment score (0 to 100), computed for each segment s:

Score(s) = 100 × ( w_L · L + w_A · A + w_R · R + w_P · P )

Factor Definition Normalisation (0 to 1)
L Lighting Street lamps within 25 m per 100 m of segment, or lit=yes tag min(1, density / 3)
A Activity Open shops, bus stops, transit stations, and restaurants within 50 m, using opening hours at the walking time min(1, count / 4)
R Community rating Shrunk mean of "felt safe" ratings: (n·mean + k·prior) / (n + k), with k = 5, prior = 0.5 0 to 1
P Proximity to help Distance to the nearest police, hospital or Safe Stop max(0, 1 − d / 500 m)

Weights by time of day:

Period w_L w_A w_R w_P
Day (06:00-18:00) 0.15 0.30 0.35 0.20
Evening (18:00-21:00) 0.30 0.25 0.25 0.20
Night (21:00-06:00) 0.40 0.10 0.30 0.20

Route score: 0.7 × length-weighted mean(segment scores) + 0.3 × minimum segment score. This penalises one very dark stretch even if the rest is good.

Cold start: with no ratings, R equals the prior (0.5), so scores come from OSM data on day one. Weights are initial defaults and shall be reviewed after pilot data. The model shall be documented in the app ("How is this score calculated?").

Fairness rule: no input may be derived from demographics, religion, caste, or neighbourhood reputation.

6.2 Composite threat score (DET-6)

S = min(100, round( (0.45·Audio + 0.30·Motion + 0.25·Context) × M_night ) + B_manual )

  • Audio and Motion are 0 to 100 from the models; Context is 100 in a segment scoring below 40, else 0 to 50 scaled by the route score.
  • M_night = 1.2 from 21:00 to 06:00. B_manual = 40 for manual SOS.
  • Pre-alert threshold: 70 (60 if the segment score is below 40). Parameters are configurable and shall be tuned using false-alarm feedback.

6.4 Offline behaviour

  1. Trigger writes the alert (UUID, location, timestamp) to SQLite as PENDING.
  2. SMS is sent immediately; the status changes to SMS_SENT.
  3. On connectivity, the app calls /alerts/sync; on success, the status is SYNCED.
  4. Duplicate UUIDs are ignored by the server.

9. Verification and Acceptance

9.1 Test strategy

  • Unit tests: scoring functions, state machine, queue logic, crypto helpers.
  • Integration tests: API with PostGIS test database; WebSocket live location; alert sync idempotency.
  • Model tests: held-out evaluation; per-class confusion matrix; threshold sweep.
  • Field tests: walk the pilot area at day and night; airplane mode scream test; SMS delivery on two carriers.
  • Security tests: PIN brute-force lockout, token expiry, WebSocket ticket reuse, encrypted evidence cannot be decrypted by the server.
  • Usability tests: 5 to 10 target users complete onboarding, a walk and a false alarm cancel without help.
  • Device matrix: at least 3 Android devices across vendors (battery optimisation behaviour differs).

  1. Set up a development build, repository, CI and Docker Compose (day 1).
  2. Load the pilot-area OSM extract; implement segment scoring and /routes/compare.

10.5 Risks and mitigations

Risk Impact Mitigation
Expo Go incompatibility with native modules Blocks testing Use a development build from day 1
Audio model false positives Alert fatigue Pretrained embeddings, 3-of-5 rule, PIN cancel, feedback loop, report numbers honestly
Sparse OSM data in the area Weak scores Verify coverage early; add manual surveys and pre-loaded ratings for the demo area
Android background limits Tracking stops Foreground service with correct types, battery exemption guide, test on several OEMs
SMS delivery or DLT blocks Alert not delivered Native phone SMS for offline path; register DLT early; test two carriers
Fake or malicious ratings Biased scores RATE-2/3 rules, anonymisation, moderator review
Privacy complaints Trust loss Minimisation, consent screens, clear retention, no demographic inputs
Over-claiming Credibility Use the wording rules ROUTE-8, EVID-6; label mockups as concepts
